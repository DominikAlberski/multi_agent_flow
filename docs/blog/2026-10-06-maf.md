# maf: a team of AI coding agents, built from files and a CLI

I run more than one AI coding agent on one repository.
One agent plans. Two agents write code. One agent reviews.
Each agent runs in its own terminal, and often in a different harness:
Claude Code, opencode, Codex, or Hermes.

Without help, this setup fails fast.
Two agents edit the same file.
The reviewer waits for a message that nobody sends.
The planner does not know that the developer stopped an hour ago.

maf (multi_agent_flow) is the coordination layer that I built for this problem.
This post explains what maf does, how it works, and what I learned.

## The idea: CLI and files only

maf has no server, no GUI, and no vendor SDK.
Every harness can run a shell command and read a file.
So maf uses only shell commands and files.

maf has three parts:

| Part | Implementation |
|---|---|
| Communication | A Taskwarrior task board and a file inbox, through the `coord` CLI |
| Resource control | Locks that use `mkdir`, so they work on macOS and Linux |
| Shared memory | A graphify knowledge graph and an Obsidian vault, served over MCP |

Each agent uses the same `coord` commands.
It does not matter which harness runs the agent.

## Words that maf uses

maf uses a small, fixed vocabulary:

- A **harness** (Claude Code, opencode, Codex, Hermes) runs a **role** (architect, tester).
- A running instance of a role is a **worker**, for example `tester-1`.
- A **task** belongs to a role. A worker **claims** a task.
- A **message** goes to the inbox of a role.
- A worker holds a **lock** on a shared resource.

Two roles are **lead roles**.
The **project manager** talks to you, creates goals, and reports back.
The **architect** splits a goal into tasks and assigns them.
Lead roles do not write code, and they never claim tasks.

## Five minutes to a team

Link the `maf` command into your `PATH` once:

```sh
ln -sf "$PWD/bin/maf" ~/.local/bin/maf
```

Then go to your project and add agents:

```sh
cd ~/Projects/my-app
maf add claude:architect opencode:backend-developer claude:reviewer
maf start claude architect
```

Each argument is `HARNESS:ROLE`.
`maf start` creates a git worktree for the worker and starts the harness in it.
So each worker has its own branch and its own files.

You can also let an agent do the setup.
Open any coding agent in your project and give it `install.md`.
The agent asks which harnesses and roles you want, and then runs `maf add`.

## maf stays out of your git

maf is a tool. It is not a part of your project.
So maf commits nothing and edits no file that your project tracks.

All maf files go into one folder, `.maf/`.
maf lists that folder and each link it creates in `.git/info/exclude`.
That file is local to your clone.

maf gives its configuration to each harness on the command line.
Claude Code gets its hooks through `--settings` and its MCP server through `--mcp-config`.
Your own `CLAUDE.md`, `AGENTS.md`, and `.mcp.json` stay as they are.

If you remove maf, you keep the work of the agents:
the code, the decision records in `docs/decisions/`, and `GLOSSARY.md`.

## Workflows as text

A workflow tells the architect what to do in each stage.
maf has three default workflows: `simple`, `plan-review`, and `tdd`.
The `plan-review` workflow looks like this:

```text
Stage 1. Write the plan. Create one review task for the reviewer. Wait for approval.
Stage 2. Commit the approved plan on the goal branch.
         Create one implementation task per part of the plan.
Stage 3. After each implementation task is done, create one review task.
Stage 4. Merge the approved branches. Close the goal.
```

The workflow is plain text in `.maf/workflow.md`.
I did not add a workflow schema or a workflow engine.
The architect reads the text and acts on it.
A task for the next stage does not exist before the gate passes.
So no agent can claim the task too early, and maf needs no dependency field.

## Lessons from real runs

Most of the design came from failures.
Here are four of them.

### A message is useless if nobody reads it

The architect did not read a decision request for hours.
The architect had no running session, and no process woke it up.

Now `coord msg` checks each receiver role.
If a role has no live worker and no message hook, `coord` prints a warning.
The **dispatcher** fixes the gap.
The dispatcher polls the board and the inbox.
When work arrives, it starts a one-shot agent run for the role.

### Prose rules are not walls

A role file said "the reviewer does not edit files."
On one harness, the reviewer edited files anyway.

Now maf installs a git `pre-commit` hook.
The hook refuses a commit from a role that cannot edit.
An agent can skip the hook with `--no-verify`.
The hook stops mistakes, not attacks.

### No conflict does not mean no defect

Two tasks changed different lines of one file.
Git reported no conflict, but the result was broken.

Now a worker merges the goal branch into its task branch before it finishes.
Then the worker runs the tests again.
`coord done` refuses if the task branch does not contain the head of the goal branch.

### Repeated calls cost more than large files

One run used 10.2 million input tokens.
Large files did not cause most of the cost. Repeated calls did.
Each model call sends the whole context again.

The Codex project manager polled the board with `sleep`.
That loop made 93 model calls and used 4.69 million input tokens.

Now an agent runs `coord await` and ends its turn.
A hook waits for work outside the model.
The model sees no tokens until work arrives.
One avoided poll call saves about 45,000 tokens.

Other changes in the same work:

- `coord msg --fyi` sends a message that does not start a run.
- Dispatched runs start lean: no plugins, no extra MCP servers, no slash commands.
- After a usage limit, the dispatcher pauses for 15 minutes, and doubles the pause up to one hour.
- The dashboard shows the cache hit ratio and the cache writes of each run.

## What maf does not do

I keep a log of features that I reject on purpose: `docs/out-of-scope.md`.
Some examples:

- **Sandbox providers** such as Docker. Each worker runs in a git worktree on the host.
  If you need isolation, run the whole project in a container.
- **Session fork.** Each harness stores sessions in its own format.
  A fresh session with a handoff note gives most of the value.
- **A coordination git branch.** The coordination state is not committed.

This log saves time.
Before I add a feature, I read the log and the reason.

## Try it

maf needs Ruby 3.0 or later, Taskwarrior, and a git project with one commit.
graphify is optional.

Start with `GETTING_STARTED.md`.
It walks you through a two-agent workflow by hand.
Then read `USER_MANUAL.md` for the full team setup with the dispatcher and the dashboard.
